## What is CSRF?

Cross-site request forgery is a vulnerability that tricks a logged-in user into performing an action they did not intend to perform. It works around the same origin policy, which normally stops one site from interfering with another.

Three things have to be true at the same time for an attack to land:

- The action is worth forging. Changing a language preference is not, changing an email address or a password is.
- The application identifies the user with a cookie and nothing else. No tokens, no other mechanism tied to the session.
- The attacker can work out every parameter the request needs. If there is a random value in there that cannot be guessed, the attack fails.

If the action can be triggered with `GET`, the whole attack fits in one tag:

```html
<img src="https://vulnerable-website.com/email/change?email=pwned@evil-user.net">
```

## Common defences against CSRF

- **CSRF tokens.** A unique, secret, unpredictable value generated by the server and given to the client. The client has to send it back with any sensitive action, which makes forging a request much harder.
- **SameSite cookies.** A browser mechanism that decides when a cookie is attached to a request coming from another site. Since 2021 Chrome applies `Lax` by default when a site does not set a value, and other browsers are expected to follow.
- **Referer validation.** The application checks that the request came from its own domain. Weaker than token validation, and easy to get wrong.

## What is a CSRF token?

A CSRF token is a secret, unpredictable value that the server generates and hands to the client. The client must include it when it performs a sensitive action, and the server refuses the action without it.

The usual delivery method is a hidden field in the form:

```html
<form name="change-email-form" action="/my-account/change-email" method="POST">
  <label>Email</label>
  <input required type="email" name="email" value="example@normal-website.com">
  <input required type="hidden" name="csrf" value="50FaWgdOhi9M9wyna8taR1k3ODOR8d6u">
  <button class='button' type='submit'> Update email </button>
</form>
```

## Ways to test

- Try changing `POST` to `GET`.
- Try removing the token completely. Some implementations only validate when a token is present.
- Try a token from your own session on someone else's. If it works, the token is not tied to the session.
- Try a token tied to a non-session cookie, if the cookie can be set from a related scope. A cookie-setting function on `staging.demo.normal-website.com` may be able to place a cookie that gets sent to `secure.normal-website.com`.
- Try a token that is simply duplicated in a cookie. If the two copies only need to match, you can invent both.
- Try bypassing SameSite restrictions. Since 2021 Chrome applies `Lax` when the site sets nothing, and `Strict` can sometimes be worked around through a same-site redirect.
- Try the `Referer` header. Remove it, or spoof it.

## What is a site in the context of SameSite cookies?

A site is the top-level domain plus one level, usually written as TLD+1. For SameSite purposes the scheme counts too, so `http://app.example.com` to `https://app.example.com` is cross-site in most browsers.

## What's the difference between a site and an origin?

An origin is narrower. Two URLs share an origin only if the scheme, domain, and port all match. A site covers several domains, so a cross-origin request can still be same-site, but not the other way around.

| Request from | Request to | Same-site? | Same-origin? |
| --- | --- | --- | --- |
| `https://example.com` | `https://example.com` | Yes | Yes |
| `https://app.example.com` | `https://intranet.example.com` | Yes | No: mismatched domain name |
| `https://example.com` | `https://example.com:8080` | Yes | No: mismatched port |
| `https://example.com` | `https://example.co.uk` | No: mismatched eTLD | No: mismatched domain name |
| `https://example.com` | `http://example.com` | No: mismatched scheme | No: mismatched scheme |



The distinction matters because anything that gives you JavaScript execution on one domain also lets you get around site-based defences on its siblings.

Browsers support three levels, set with the `SameSite` attribute:

`Set-Cookie: session=0F8tgdOhi9ynR1M9wa3ODa; SameSite=Strict`

### Strict

The cookie is never sent on a cross-site request. If the site in the address bar does not match the site the request is going to, the cookie stays home. This is what you want for cookies that can change data or reach sensitive pages, and it can break cross-site functionality.

### Lax

The cookie is sent on cross-site requests only if the request is a `GET` and it came from a top-level navigation, such as a link the user clicked. Cross-site `POST` requests do not get it, and neither do background requests from scripts, iframes, or images.

### None

SameSite is switched off, and the cookie goes out on every request to the site that set it, including requests from unrelated third parties. Chrome treats a missing attribute as `Lax`, but other browsers historically treated it as `None`. A cookie set with `SameSite=None` must also carry `Secure`, or browsers reject it.

### Bypassing SameSite Lax restrictions using GET requests

Servers are not always strict about which method reaches an endpoint, even one that expects a form submission. If the session cookie is `Lax` and the endpoint accepts `GET`, a top-level navigation still carries the cookie:

```html
<script>
  document.location = 'https://vulnerable-website.com/account/transfer-payment?recipient=hacker&amount=1000000';
</script>
```

If a plain `GET` is refused, some frameworks let you override the method. Symfony accepts a `_method` parameter that wins over the real method for routing:

```html
<form action="https://vulnerable-website.com/account/transfer-payment" method="GET">
  <input type="hidden" name="_method" value="POST">
  <input type="hidden" name="recipient" value="hacker">
  <input type="hidden" name="amount" value="1000000">
</form>
```

Other frameworks have their own equivalent.

## Referer

### Skip sending it at all

If the application only checks `Referer` when it is present, then removing it skips the check. A meta tag in the attacking page does it:

`<meta name="referrer" content="never">`

### Validation of Referer can be circumvented

Naive validation is easy to beat. If the check is that the domain starts with the expected value, put the expected value in a subdomain of your own:

`http://vulnerable-website.com.attacker-website.com/csrf-attack`

If the check is that the domain appears anywhere in the header, put it in the query string:

`http://attacker-website.com/csrf-attack?vulnerable-website.com`

That second one often works in Burp and then fails in a browser, because browsers strip the query string from `Referer` to avoid leaking sensitive data. The exploit server can override that with `Referrer-Policy: unsafe-url`, which keeps the full URL including the query string. Note the spelling: the header is `Referrer-Policy` and the request header is `Referer`.
